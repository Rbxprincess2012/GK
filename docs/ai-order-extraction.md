# ИИ-нормализация заявки (LLM extraction)

Шаг «свободный текст клиента → заявка» из [дизайна Этапа 2](superpowers/specs/2026-05-31-stage2-bot-automation-design.md).
Модель: **YandexGPT** (`gpt://<folder_id>/yandexgpt/latest`), вызывается из n8n (узел HTTP Request).
Folder и сервисный аккаунт — см. память `stage2-roadmap`.

## Принцип

Не пытаемся раскладывать по структурным полям всё подряд (действие, тип, класс, номера
баков, срочность, условия) — ситуаций бесконечно много. Извлекаем только **минимальное
ядро для маршрутизации и планирования**, а операционную суть **перефразируем в строгий
текст-задание для водителя**.

Извлекаем в поля:
- **client_hint** — заказчик, если назван в сообщении (обычно клиент уже определён по каналу);
- **object_hint** — адрес/объект (текст для резолва `object_id` в n8n);
- **desired_date** — желаемая дата заезда (только если явно названа);
- **desired_time** — желаемое время заезда.

Всё прочее (что сделать, сколько, № баков, класс отхода, срочность, погода и т.п.) → в
**task_text**: короткая деловая формулировка от третьего лица, например
*«Клиент просит срочно заменить контейнеры №32 и №56»*.

## Контракт

```json
{
  "orders": [
    {
      "client_hint": "строка или null",
      "object_hint": "строка или null",
      "desired_date": "ГГГГ-ММ-ДД или null",
      "desired_time": "ЧЧ:ММ или null",
      "task_text": "строгая формулировка задания для водителя"
    }
  ]
}
```

Разные адреса/объекты в одном сообщении → несколько элементов `orders`.

## Маппинг на бэкенд (n8n)

- `object_hint` → резолв в `object_id` (по объектам клиента канала); неоднозначно → бот уточняет.
- `desired_date` / `desired_time` → одноимённые поля заявки.
- `task_text` → `orders.note` (его и видит диспетчер при согласовании, и водитель в задании).
- Затем `POST /orders { object_id, status:'pending_review', desired_date, desired_time, note, items:[…] }`.

> ⚠️ Открытый момент по бэкенду: `createOrder` сейчас требует `items.min(1)` со структурой
> (action/container_type_id/quantity). При лёгком приёме структурных `items` у нас нет —
> их при согласовании проставляет диспетчер. Нужно решить: (а) разрешить `pending_review`
> создавать без `items` (note — источник правды для водителя), либо (б) хранить черновики в
> отдельной таблице `order_drafts` без жёсткого FK. Решаем на этапе сборки воркфлоу/бэка.

## Системный промпт (YandexGPT, temperature 0)

```
Ты ассистент диспетчера вывоза отходов. Из сообщения клиента извлеки заявку(и) и верни ТОЛЬКО JSON, без markdown и без пояснений. Схема: {"orders": [ {"client_hint": строка или null, "object_hint": строка или null, "desired_date": "ГГГГ-ММ-ДД" или null, "desired_time": "ЧЧ:ММ" или null, "task_text": строка} ]}. В отдельные поля извлекай ТОЛЬКО: заказчика (client_hint, если назван), адрес или объект (object_hint), желаемую дату (desired_date) и время заезда (desired_time). Всё остальное — что нужно сделать, количество, номера контейнеров, класс отхода, срочность, условия — НЕ раскладывай по полям, а перескажи короткой деловой формулировкой от третьего лица в task_text, например: Клиент просит срочно заменить контейнеры №32 и №56. Если в сообщении несколько разных адресов или объектов — верни несколько элементов orders. desired_date заполняй ТОЛЬКО если дата явно названа, включая слова сегодня, завтра, послезавтра; иначе null. Сегодня 2026-06-02. task_text всегда заполнен, по-деловому, без эмоций и воды, но с конкретикой (что сделать, сколько, номера баков, класс, срочность).
```

> «Сегодня 2026-06-02» в проде подставляется динамически (n8n, дата по Europe/Moscow).

## Петля обучения (feedback loop, не файнтюн)

YandexGPT онлайн не дообучается. «Самообучение» делаем через обратную связь:

1. **Захват.** На каждом черновике храним `order_drafts.llm_extraction` — исходную выдачу ИИ.
   При `promote` диспетчер правит поля → дельта «ИИ → факт» = обучающий сигнал.
2. **Few-shot.** Из исправленных пар «сообщение → верная структура» копим небольшой
   набор и подмешиваем свежие примеры в системный промпт (in-context learning). Точность
   растёт без файнтюна, в пределах токенного бюджета.
3. **Подсветка паттернов.** Агрегируем `ambiguities[]` (ИИ сам флагает неуверенность) +
   повторяющиеся темы в `task_text`/правках. Тема всплывает часто → показываем директору
   предложение: «завести отдельное поле/жёсткий параметр в заявке?».
4. **Изменение схемы — только с подтверждения человека.** Добавление «жёсткого параметра» —
   это миграция; система предлагает, директор решает. Не автоматически.

Минимальный фундамент уже в БД: `llm_extraction` (исходный JSON ИИ) + `ambiguities`.
Следующие шаги (few-shot подмешивание, агрегатор паттернов, экран предложений) строятся
поверх этого сигнала.
