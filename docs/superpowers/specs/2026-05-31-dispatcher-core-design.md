# Диспетчерская система вывоза отходов — дизайн ядра (Этап 1)

Date: 2026-05-31

## Problem Statement

Компания вывозит отходы в контейнерах («лодочках») по объектам заказчиков
(г. Краснодар и окрестности). Сейчас весь процесс — ручной:

- Заявки приходят по **множеству каналов**: чаты и голосовые в Telegram, мессенджер
  MAX, телефонные звонки. С каждым заказчиком и каждым водителем — **отдельный чат**
  (50+ чатов).
- Диспетчер вручную переписывает заявки в **Excel**, по памяти раскидывает их на
  водителей смены, ориентируясь по районам (**частые ошибки по географии**), стараясь
  дать всем поровну.
- Назначение водителю отправляется вручную — текстом в его чат.
- Водитель закрывает работу фото/голосом/текстом в чат; диспетчер вручную пересылает
  это в чат заказчика. Заявка считается закрытой по факту отправки.
- Счета выставляются на почту заказчика.

Боль не в форме создания заявки, а в **омниканальном приёме, ручной транскрибации,
ручной маршрутизации туда-обратно** и в Excel как «базе данных».

## Цель и фазирование

Стратегия — сначала фундамент, потом автоматика:

- **Этап 1 (этот документ):** правильная структурированная БД + рабочая логика на
  фронте. Данные вносятся **вручную, как и раньше**, но в структуру, а не в Excel.
  Цель — уйти от Excel и выстроить корректный «скелет» процесса.
- **Этап 2 (за рамками реализации, но архитектурно учтён):** модули автоматизации на
  n8n — омниканальный приём, транскрибация голоса, Telegram/MAX-боты, авто-отчёты
  клиенту, гео-расчёты топлива, генерация/отправка счетов.

Никакие интеграции каналов на Этапе 1 не строятся; под них закладывается структура.

## Requirements

### Функциональные (Этап 1)

1. **Заказчики**: юрлицо/ИП, реквизиты для счетов, неоф. ник, email, способ оплаты по
   умолчанию, признак «требует фото-подтверждение».
2. **Объекты** заказчика: адрес (улица + дом), неоф. название, **район** (из улицы),
   опц. переопределение «требует фото». Текущий инвентарь контейнеров.
3. **Контейнеры** как единицы учёта с уникальными номерами: тип, состояние
   (пустой/полный), текущее местоположение (склад/объект/в рейсе).
4. **Машины**: госномер, ёмкость в лодочках (по умолч. 3), норма расхода топлива,
   статус (рабочая/сломана/в ремонте), пробег. Мягкая привязка к водителю.
5. **Водители**: имя, телефон, активность, машина по умолчанию.
6. **График/Календарь** как самостоятельная сущность с подробным визуалом: план +
   факт (вышел/болеет/отпуск), день/ночь, назначенная машина.
7. **Заявки**: объект, позиции `действие × тип × количество`, способ оплаты
   (переопределяемый), желаемые дата/время, статусная модель.
8. **Распределение**: борд — нераспределённые заявки, сгруппированные по району;
   доступные сегодня водители с машиной и счётчиком загрузки/слотов.
9. **Исполнение и закрытие**: фиксация **фактических номеров** контейнеров (движения),
   обновление инвентаря; вложения (фото/аудио/текст + расшифровка), опционально.
10. **Маршрут/рейс за день**: упорядоченная последовательность объездов водителя.
11. **Счета**: лёгкая сущность (заказчик, заявка, сумма, статус, способ).
12. **Справочник улиц→районов** г. Краснодара (seed из официального реестра).

### Нефункциональные

- Транзакционная целостность критичных операций (закрытие заявки атомарно меняет
  движения + контейнеры + статус).
- Один источник истины по инвентарю (вывод из `containers`, без дублирующего счётчика).
- Схема версионируется миграциями; входные данные валидируются.
- Архитектура готова к подключению модулей Этапа 2 без переделки ядра.

## Proposed Solution

**Тонкий бэкенд (Node.js + Express + PostgreSQL)** обслуживает приложение через REST.
n8n остаётся **только под автоматизацию Этапа 2** (то, в чём он силён — интеграции),
работая с той же базой/через API.

Обоснование: модель богатая и транзакционная (инвентарь, движения контейнеров, маршруты,
статусные переходы), будет расти. n8n как основной CRUD-API на такой модели быстро
превращается в нечитаемую кашу из нод без валидации и транзакций. Чистая бизнес-логика —
в коде бэкенда.

## Architecture

```
Браузер (React, фронт уже есть)
   │  REST (axios, src/lib/api.js)
   ▼
Express API  ──(слои: routes → controllers → services → db)
   │  Knex (миграции + запросы), транзакции
   ▼
PostgreSQL (Timeweb managed)
   ▲
   │  Этап 2: n8n читает/пишет ту же базу / ходит в API
   └── n8n (Telegram/MAX/транскрибация/гео-топливо/счета)
```

- **Фронт** уже реализован как React + Vite + Zustand с моками; на Этапе 1 действия
  сторов заменяются вызовами `api.js`, добавляются новые экраны.
- **Бэкенд** — новый сервис в репозитории (напр. `server/`): Express, Knex-миграции,
  валидация (zod), сервисный слой с транзакциями.
- **БД** — PostgreSQL на Timeweb (уже развёрнут).

## Implementation Details

### Доменная модель — жизненный цикл заявки

```
Приём (вручную) → Заказчик/Объект (завести при необходимости)
  → Создание заявки (позиции: действие × тип × кол-во, способ оплаты)
  → Распределение (водитель смены, по району, поровну, ёмкость 3 слота)
  → Выдача задачи водителю (Этап 1: вручную в чат)
  → Исполнение (фиксация фактических номеров контейнеров → инвентарь)
  → Закрытие у водителя (вложения, опц.)
  → Отчёт заказчику (Этап 1: вручную) → статус «закрыта»
  → Счёт на почту
```

### Схема PostgreSQL (таблицы и ключевые поля)

**Стороны и справочники**

- `clients` — `type (ooo|ip)`, `legal_name`, `inn`, `kpp?`, `ogrn`, `legal_address`,
  `bank_name`, `bank_account`, `bik`, `corr_account`, `nickname`, `email`,
  `default_payment_method (cashless|cash)`, `requires_photo bool`, `phone`, `created_at`.
- `districts` — `name` (округ: Прикубанский/Карасунский/Центральный/Западный +
  сельские), `kind (city|rural)`.
- `streets` — `name`, `district_id`. Возможны дубли (улица в нескольких округах) —
  при выборе уточняется. Seed из реестра (см. ниже).
- `objects` — `client_id`, `street_id?`, `address_raw`, `house`, `building?`,
  `informal_name`, `district_id` (по улице, с возможностью уточнения), `requires_photo?`
  (override), `lat?`, `lng?` (Этап 2), `note`.
- `container_types` — `name` (по умолч. «стандартный»/лодочка), `volume?`.
- `containers` — `number` (uniq), `type_id`, `state (empty|full)`,
  `location (warehouse|object|in_transit)`, `object_id?`.
- `vehicles` — `gov_number` (uniq), `capacity_slots default 3`, `fuel_norm`,
  `status (active|broken|repair)`, `mileage`, `model?`.
- `drivers` — `name`, `phone`, `is_active`, `default_vehicle_id?`.

**График (план + факт) — отдельная сущность**

- `shifts` — `driver_id`, `date`, `shift_type (day|night)`,
  `status (planned|present|sick|vacation|absent)`, `vehicle_id?`, `note`.
  Уникальность по (`driver_id`,`date`,`shift_type`). Календарь читает её; на
  распределении доступны только `status = present`.

**Заявка: намерение и факт раздельно**

- `orders` — `id` (PK, внутренний технический ключ),
  `number (serial, uniq)` — человекочитаемый **сквозной ID заявки** для общения с
  заказчиком/водителем и для счёта, `client_id`, `object_id`,
  `payment_method` (по умолч. из клиента), `desired_date?`, `desired_time?`,
  `status (new|assigned|in_progress|done|closed|cancelled)`, `assigned_driver_id?`,
  `vehicle_id?`, `shift_date?`, `shift_type?`, `note`, `created_at`, `done_at?`,
  `closed_at?`.
- `order_items` *(намерение)* — `order_id`, `action (place|replace|haul)`,
  `container_type_id`, `quantity`, `waste_class (4|5)` *(информационно)*.
- `order_item_containers` *(опц. — заказчик назвал конкретные номера)* —
  `order_item_id`, `container_id`. Заполняется, только когда клиент просит забрать
  конкретные контейнеры (подмножество `quantity`); иначе пусто — водитель берёт любые.
- `container_movements` *(факт)* — `order_id`, `container_id`,
  `direction (delivered|picked_up)`, `object_id`, `created_at`.
- `attachments` — `order_id`, `kind (photo|audio|text)`, `file_url`, `transcript?`,
  `author_driver_id?`, `created_at`.

**Маршрут / деньги / настройки**

- `routes` — `driver_id`, `vehicle_id`, `date`, `shift_type`. Остановки:
  `route_stops` — `route_id`, `seq`, `stop_type (object|landfill|base)`, `order_id?`,
  `object_id?`. Этап 1: последовательность объездов заявок; Этап 2: авто-вставка
  заездов на свалку по ёмкости + расстояния.
- `invoices` *(лёгкая)* — `client_id`, `order_id?`, `amount`, `status (issued|paid)`,
  `method`, `issued_at?`, `paid_at?`.
- `settings` — адрес+гео **базы** и **свалки** (свалка одна); параметры (погрешность
  топлива и т.п.).

**Каркас под Этап 2 (структура есть, наполнение позже)**

- `channels` — `owner_kind (client|driver)`, `owner_id`, `type (telegram|max|phone)`,
  `external_id` (chat_id).
- `inbound_messages` — `channel_id`, `raw_text`, `media_url`, `transcript`,
  `received_at`, `linked_order_id?`.

### Ключевые решения схемы

1. **Инвентарь объекта выводится из `containers`** (`WHERE object_id=X AND
   location='object'`), без отдельного счётчика — один источник истины.
2. **Намерение (`order_items`) ≠ факт (`container_movements`)**: обычно заказчик видит
   «заменить 2», система фиксирует реальные номера при закрытии. Но если заказчик сам
   назвал конкретные номера — они хранятся в `order_item_containers` (опционально) и
   подсказываются водителю/диспетчеру при исполнении.
3. **`shifts` хранит план и факт** одним статусом — болезнь/отпуск это статус строки.
4. **Машина — отдельная сущность**, к водителю привязана мягко (default + факт в смене).
5. **Район — на улице, не на объекте**: консистентная группировка против гео-ошибок.
6. **`waste_class` информационный** — свалка одна, маршрут классом не определяется.

### Транзакционные операции (сервисный слой)

- `POST /orders/:id/assign` `{driver_id, shift_date, shift_type, vehicle_id?}` →
  статус `assigned`.
- `POST /orders/:id/complete` `{movements:[{container_id,direction}], attachments[]}` →
  **транзакция**: вставка движений + обновление `containers.location/state/object_id` +
  статус `done` + `done_at`.
- `POST /orders/:id/close` → статус `closed` + `closed_at` (после отправки заказчику).

### REST-эндпоинты (обзор)

- `clients` CRUD (+ вложенные `objects`); `objects` CRUD (+ текущий инвентарь).
- `districts`, `streets` (чтение + поиск; create при заведении новой улицы).
- `container-types`, `containers` CRUD (фильтр по объекту/местоположению).
- `vehicles` CRUD; `drivers` CRUD.
- `shifts` — `GET ?from&to`, upsert строки водитель×дата.
- `orders` CRUD + переходы `assign` / `complete` / `close`; фильтры по статусу/дате/
  водителю/району.
- `routes` — построение/чтение дневного маршрута, изменение порядка остановок.
- `attachments` (загрузка), `invoices` (лёгкое), `settings`.

### Фронт (React) — экраны

Существующие расширяются, добавляются новые:

- **Заказчики** — реквизиты, способ оплаты по умолч., email, «требует фото»; вложенные
  **Объекты** (улица из справочника → район автоподстановкой, дом, неоф. название).
- **Объекты** — карточка с текущим инвентарём.
- **Контейнеры** — реестр единиц (номер, тип, состояние, местоположение).
- **Машины** — реестр (госномер, ёмкость, норма топлива, статус, водитель по умолч.).
- **Календарь смен** — подробный визуал: сетка месяц/неделя, водитель×дата, статус
  (вышел/болеет/отпуск), назначенная машина.
- **Распределение** — главный экран: слева нераспределённые заявки по районам; справа
  доступные сегодня водители (present + машина + счётчик загрузки/слотов).
- **Цикл заявки** — создать → назначить → закрыть у водителя (ввод номеров контейнеров +
  вложения) → отправить заказчику (статус «закрыта»).

Действия Zustand-сторов заменяются вызовами `src/lib/api.js`.

### Seed: улицы → районы (г. Краснодар)

Источник — `9609544.docx` (официальный «Перечень автомобильных дорог местного значения
МО город Краснодар»). Структура строки: № / название улицы / протяжённость / ID /
**принадлежность округу**. ~2046 улиц.

Округа (нормализуем как `districts`):
- Городские: **Прикубанский, Карасунский, Центральный, Западный**.
- Сельские: Калининский, Старокорсунский, Берёзовский, Елизаветинский, Пашковский
  (+ посёлки/станицы/хутора — хранить опционально как уточнение).

Обработка при импорте:
- нормализация пробелов и комбинированных значений;
- улицы, пересекающие несколько округов, дают несколько строк `streets` → при выборе
  диспетчер уточняет округ;
- granularity — уровень округа («хоть как-то группировать»); посёлок/станица —
  опциональное уточнение.

## Testing Strategy

- **Юнит-тесты сервисов** (бизнес-логика): корректность транзакций `complete`/`close`
  (движения ↔ инвентарь ↔ статус), переопределение способа оплаты, недоступность
  распределения на не-`present` водителей.
- **Тесты инвентаря**: место → объект, замена (±0), установка (+N), вывоз (−N); вывод
  остатка из `containers` совпадает с ожидаемым после серии движений.
- **Интеграционные тесты API** на тестовой БД (миграции + сидинг), happy-path и
  валидация ошибок.
- **Тест импорта seed**: парсинг docx → нормализация → ожидаемое число улиц/округов,
  обработка пересекающих округа улиц.
- **Фронт**: smoke-тесты ключевых экранов (создание заявки, распределение, закрытие).

## Rollout Plan

**Этап 1 (реализация ядра)**

1. Поднять бэкенд-скелет (Express + Knex + миграции) и подключить к Postgres Timeweb.
2. Миграции схемы ядра; импорт seed улиц→районов из реестра.
3. REST + сервисный слой по ресурсам и транзакционным операциям.
4. Перевести фронт со сторов-моков на `api.js`; добавить экраны (Объекты, Контейнеры,
   Машины, Календарь, Распределение, цикл заявки).
5. Параллельный прогон с Excel, сверка, отказ от Excel.

**Этап 2 (модули автоматизации на n8n, поверх готового ядра)**

- Омниканальный приём (Telegram/MAX/звонки) → `inbound_messages` + транскрибация.
- Авто-выдача задачи водителю и авто-отчёт заказчику в его канал.
- Гео-расчёт маршрута и топлива (база → объект → свалка → … → база) × норма × погрешность.
- Генерация и отправка счетов на почту.

- Авторизация бэкенда (сейчас на фронте mockAuth; на Этапе 1 — реальные сессии/JWT?).
