# Проверка пруфов и сообщения клиенту — дизайн

Дата: 2026-06-10

## Постановка задачи

Две связанные задачи в работе менеджера/директора:

1. **Проверка пруфов.** Водитель через бота прикладывает медиа-доказательства выполнения
   по каждому участку (фото/видео/голос/текст). Данные уже копятся в `attachments`, но в
   админке их **нигде не видно** и нет модерации. Нужен просмотр + приёмка/возврат на переделку.

2. **Сообщение клиенту без клиентского бота.** Клиент может не ставить клиентский бот.
   У менеджера должна быть возможность быстро сформировать сообщение клиенту в личный
   мессенджер (Telegram/MAX). Сообщение формируется **только после приёмки заявки менеджером**
   и параллельно уходит в `outbox` для ботов (если бот не подключён — просто в пустоту, без
   ретроактивной досылки; подключат позже — пойдёт структурно по новым заявкам).

   **Решение по оперативным проблемам на объекте (принято заказчиком):** автоматического
   мгновенного оповещения клиента об инциденте (`failed`-участок) НЕ делаем. Срочную проблему
   («нет доступа», «ворота закрыты») водитель решает **звонком доверенному лицу** — его телефон
   уже кликабелен в карточке бота. Вся клиентская отправка (диплинк + бот) идёт **только после
   аппрува менеджера**. Так канал один и предсказуемый, без полу-автоматики.

## Требования

**Функциональные:**
- Менеджер/директор видит пруфы по заявке: и в карточке заявки (галерея по участкам), и в
  отдельной ленте-очереди «Проверка».
- Модерация на уровне под-задачи (участка): «Принять» / «Вернуть на переделку» (с комментарием).
- Возврат на переделку: участок → `pending`, заявка (если была `done`) → `in_progress` к **тому же**
  водителю; водителю прилетает уведомление в бот «переснимите пруф».
- При приёмке **всей** заявки (все под-задачи `accepted`) генерируется:
  - публичный бессрочный фотоотчёт `https://putevo.su/r/<token>`;
  - текст сообщения по шаблону (для копирования в личный чат, диплинк на номер клиента);
  - событие в `outbox` для ботов.
- Лог сформированных сообщений (что/кому/когда/каким менеджером/в какие каналы).

**Нефункциональные:**
- Не ломать существующий конвейер статусов заявки (статус `review` уже занят проверкой *до* выезда).
- Файлы пруфов — своё хранилище `/media` (уже есть). URL'ы — неугадываемые UUID.
- Публичный отчёт — read-only, без логина, по токену; **бессрочный, без отзыва** (решение заказчика).
- Мультитенантность (будущий SaaS) не блокировать.

## Предлагаемое решение

### Часть A. Проверка пруфов

**Модель данных** — новая миграция `033_proof_review.js`. На `order_subtasks` добавляем
ось проверки пруфов, отдельную от lifecycle-статуса заявки:
- `proof_status` enum `unreviewed | accepted | rejected`, default `unreviewed`
- `reviewed_by` → `users.id` (SET NULL), `reviewed_at` timestamp, `review_comment` text
- `reject_count` int default 0

Почему отдельное поле, а не статус заявки: статус `review` в конвейере означает проверку
*до* выезда; проверка пруфов — *после* выполнения. Разные оси, не смешиваем.

**UI 1 — галерея в карточке заявки** (`src/components/admin/OrderModal.jsx`):
в блоке «Участки» под каждой под-задачей — лента вложений:
- фото/видео → миниатюры, клик → лайтбокс;
- голос → плеер; текст-пруф → цитата.
Под каждым участком кнопки `✅ Принять` / `↩ Вернуть на переделку` (модалка с комментарием).
Данные: `GET /orders/:id` дополняем `attachments`, сгруппированными по `subtask_id`.

**UI 2 — лента «Проверка»** (новая страница `src/pages/ProofReview.jsx`, пункт меню для
`manager|director`): очередь заявок, где есть `done` под-задачи с `proof_status = unreviewed`.
Фильтры дата/водитель. Карточка = заявка + превью пруфов + те же кнопки. Кнопка «Принять все
в заявке».

**Эндпоинты:**
- `POST /subtasks/:id/accept` → `proof_status=accepted`, `reviewed_by/at`.
- `POST /subtasks/:id/reject` `{ comment }` → `proof_status=rejected`, `reject_count++`,
  под-задача `status=pending`; если заявка была `done` → `in_progress` (тот же водитель);
  `outbox` событие `proof_rejected` → бот шлёт водителю «Участок X: переснимите — <comment>».
- При приёмке, делающей **все** под-задачи `accepted` → триггерится «приёмка заявки» (Часть B).

**Раздача файлов:** список пруфов — за авторизацией (только залогиненный сотрудник);
сами файлы под `/media` остаются статикой (URL = UUID). Строгое проксирование — позже при
необходимости.

### Часть B. Сообщение клиенту при приёмке

**Триггер:** все под-задачи заявки получили `proof_status=accepted` → «заявка принята менеджером».

**Что генерится при приёмке:**
- `orders.public_token` (text, unique, nullable) — заполняется один раз при первой приёмке.
- Текст сообщения по шаблону с подстановками `{client} {number} {date} {address} {driver}
  {sections} {amount} {report_url}`.
- Событие `outbox` `client_report_ready` (payload: текст + token + per-section результаты).

**Диплинк (личный чат, ручная отправка менеджером):**
- Telegram: `https://t.me/+<phone>` — открывает чат с номером; `?text=` для номера Telegram
  **не подставляет**, поэтому текст кладём в буфер обмена + тост «Текст скопирован, вставьте в чат».
- MAX: deep-link на номер (точный формат уточнить при реализации) + копирование текста.

**Публичный фотоотчёт** `GET /r/:token` — публичный, read-only, SSR/JSON-страница:
шапка заявки + по каждому участку статус и галерея `attachments` (в проде `/media/<uuid>`,
в демо — `picsum.photos`). Бессрочный, без отзыва.

**Пример** (заявка №390, Краснодар, 3 участка, один не выполнен):

Диплинк: `https://t.me/+79180001122`

Текст (буфер + outbox):
```
Здравствуйте, ООО «Ромашка»!

Заявка №390 от 10.06.2026 — вывоз выполнен ✅

Объект: Краснодар, ул. Северная, д. 12
Водитель: Кузнецов А. · Volvo FM, Х123ХХ123

По участкам:
• Склад — вывезено, 2 контейнера 🟩
• Цех — вывезено, 1 контейнер 🟩
• Двор — не выполнен: нет доступа

Сумма: 8 500 ₽ (наличными)

Фотоотчёт: https://putevo.su/r/k7Xq2m
```

**Где в UI:** кнопка «✉ Сообщить клиенту» в карточке заявки (`OrderModal`) и в карточке клиента
(`src/pages/Clients.jsx`). В Отчётах не размещаем — там аналитика.

**Шаблоны:** хранятся в `settings`, редактируются в Настройках; из коробки 3–4 преднастроенных
(«Заявка принята», «Машина выехала», «Вывоз выполнен», «Вывоз частично»).

**Лог** — новая таблица `client_messages`: `order_id`, `template`, `body`, `public_token`,
`sent_by` (users.id), `channels` (`copied` / `outbox`), `created_at`. Статус — «сформировано/
открыто», не «доставлено» (ручной канал, доставку гарантировать нельзя).

## Поведение приёмки/возврата (сводно)

- Принять под-задачу → `accepted`.
- Все под-задачи `accepted` → приёмка заявки: public_token + текст + outbox + лог.
- Вернуть под-задачу → `rejected`+`pending`; заявка `done`→`in_progress` (тот же водитель);
  уведомление в бот. После пересъёмки и повторного `done` участок снова попадает в очередь проверки.

## Стратегия тестирования

- `subtasks` сервис: accept/reject переводы статусов, идемпотентность, «все приняты → приёмка»
  ровно один раз, public_token не пересоздаётся.
- `clientMessaging`: подстановки шаблона, корректный диплинк по телефону, запись в `client_messages`,
  событие в outbox с верным `event_key` (идемпотентность).
- `GET /r/:token`: 200 для валидного, 404 для мусора; не требует авторизации; отдаёт верные участки.
- Бот: на событие `proof_rejected` шлёт нужному водителю текст с комментарием.

## План внедрения

1. Миграции 033–035 (`NODE_TLS_REJECT_UNAUTHORIZED=0 npm run migrate`).
2. Бэкенд: accept/reject + хук приёмки + clientMessaging + публичный роут + событие боту.
3. Фронт: галерея и модерация в карточке → лента «Проверка» → модалка сообщения клиенту → шаблоны в Настройках.
4. Демо-данные: пруфы (picsum) на части под-задач демо-заявок для проверки UI.

Две подсистемы независимы — при разбивке на планы их можно вести отдельными файлами
(`proof-review` и `client-messaging`).
