# Водительский Telegram-бот: логин, смена, выполнение заявок — Design Specification (v2)

Date: 2026-06-08
Status: draft v2 (учтены два независимых ревью на полном контексте кода)

> v2 vs v1: убран «список всех водителей + PIN» (ПДн на публичном репо + брутфорс) → привязка личной ссылкой через существующий `channels.verifyCode`; зафиксировано разделение ботов по токенам (снимает конфликт push/pull с n8n); изоляция вынесена на сервер; медиа-пруф хранится у себя; согласование с уже существующими `driverConfirm/fail` и моделью `shifts` (present-by-default).

## Problem Statement

Лёгкий онбординг и рабочий инструмент для водителей в Telegram:
- водитель привязывается без трения и видит **только свою** смену и **только свои** заявки;
- закрывает боль менеджера: сейчас водители видят заказы друг друга в общем чате и спорят о справедливости. **Изоляция по `driver_id` (на сервере) убирает это архитектурно**;
- ведёт полный цикл: выход на смену (пробег) → выполнение заявок по участкам с фото/видео/текст/голос-пруфом → «Завершить заявку» → завершение смены (пробег);
- готовит **контракт событий** для клиентского бота (реализация клиента — отдельный спек).

## Requirements

### Функциональные
1. **Привязка (login) личной ссылкой.** Менеджер в карточке водителя генерит одноразовую ссылку `t.me/<driver_bot>?start=<code>` (переиспользуем `channels.issueCode`). Водитель тык → бот видит `start`-параметр → `verifyCode` → привязка `chat_id ↔ driver` в `channels` (`owner_kind='driver'`, `type='telegram'`). Список водителей не показывается никогда.
2. **Повторный вход.** После «Выйти»/смены устройства — PIN (`drivers.pin_hash`, 4–6 цифр, хеш) как лёгкий повторный фактор без участия менеджера. PIN задаёт/сбрасывает менеджер в карточке. Брут-защита: lockout по `chat_id`/водителю.
3. **Выход на смену:** подтверждение машины → пробег на старте → смена `present`. Параллельно «Задачи на завтра» (read-only).
4. **Мои задачи (сегодня):** заявки водителя по `seq`, только свои.
5. **Выполнение по под-задачам (участкам):** у каждой ✅ «Выполнено» (пруф) или ⚠️ «Не смог» (причина+фото). Кнопка **«Завершить заявку»** — коммит.
6. **Коммит заявки:** ✅ закрываются навсегда; невыполненные → в пул на перераспределение (одним куском); клиенту уходит уведомление по участкам. Переспрос, если есть незакрытые; у ⚠️ обязательна причина. После коммита заявка для водителя заблокирована.
7. **Завершение смены:** конечный пробег (`odometer_end`). Расчёт топлива — будущее (только сбор данных).
8. **Изоляция — на сервере:** резолв `chat_id → driver_id`, принудительный фильтр в сервисах; запрос чужой заявки → 403/пусто.

### Нефункциональные
- Состояние сессии в Postgres (переживает рестарт бота).
- **Отдельный bot-токен** от клиентского бота. Секрет — в `.env` (репо публичный).
- Тестируемость сервисного слоя (vitest).

## Architecture

### Ключевое решение: разделение по токенам (снимает конфликт с n8n)
- В Этапе-2 уже заложено: **водительский и клиентский боты — разные токены/боты**.
- **Водительский бот — единственный владелец Telegram-IO для СВОЕГО токена** (нативный Telegraf/grammY, long-polling на старте). Никакой гонки `getUpdates` с n8n: n8n обслуживает **клиентский** токен.
- **Исходящие водителю** бот шлёт сам, синхронно в чате. **`outbox` для водителя НЕ используется.** `outbox` остаётся pull-каналом n8n для **клиентских** событий.

### Компоненты
- **bot/** — новый сервис; весь Telegram-специфичный код (хендлеры, клавиатуры, работа с `file_id`/getFile) изолирован здесь. Без прямого SQL — через `services/*`.
- **services/driverAuth** — `issueCode` (ссылка), `verifyCode` (привязка), проверка PIN + lockout, отвязка.
- **services/driverShift** — выход на смену (upsert `shifts` present + vehicle + `odometer_start`), завершение (`odometer_end`).
- **services/subtasks** — материализация под-задач, исход, коммит заявки, перенос.
- **services/driverScope** — резолв `chat_id → driver_id`, форсированный фильтр заявок (изоляция).
- **services/botSession** — состояние FSM в `bot_sessions`.
- **media worker** — фоновое скачивание пруфа из Telegram в своё хранилище.

### FSM
```
anon → (deep-link start=code) verify → idle
anon → (есть PIN, новое устройство) awaiting_pin → idle
idle:        awaiting_start_odometer → on_shift
on_shift:    viewing_tasks → completing_subtask:<order>:<section> → on_shift
on_shift:    awaiting_end_odometer → idle
любой:       «Выйти» → отвязка → anon
```

### Карта экранов
```
/start <code>  → привязка по коду → Главное меню
/start (привязан) → Главное меню
/start (не привязан, без кода, но есть PIN на устройстве-ранее) → "Введите PIN"

Главное меню (вне смены): [🚐 Вышел на смену] [📋 Задачи на завтра] [🚪 Выйти]
   → "Машина: <гос> (сменить?)" → "Пробег на старте: ___" → ✅ на смене
Главное меню (на смене):  [📋 Мои задачи] [🏁 Завершить смену] [🚪 Выйти]
   Мои задачи → свои заявки (по seq) → заявка:
       Уч.58 [✅ Выполнено](пруф) … Уч.61 [⚠️ Не смог](причина+фото) …
       [✅ Завершить заявку] → коммит
   Завершить смену → "Пробег в конце: ___" → закрыта
```

## Implementation Details

### Изменения данных (миграции)
1. `drivers.pin_hash TEXT NULL` (scrypt). Менеджер задаёт/сбрасывает в `Drivers.jsx`. + поле «личная ссылка/код» (кнопка «Сгенерировать ссылку» → `issueCode`).
2. **Выход на смену поверх present-by-default.** Сейчас (`shifts.js`, `orders.js:124-130`) водитель `present` по умолчанию, строки в `shifts` для него может не быть. Решение: «Вышел на смену» делает **upsert** строки `shifts(driver_id,date,shift_type)` со `status='present'`, `vehicle_id`, `odometer_start`. Добавить `shifts.odometer_start INT NULL`, `shifts.odometer_end INT NULL`. **Тип смены day/night — ЗАГЛУШКА:** колонка `shifts.shift_type` остаётся (enum, дефолт `day`), но НИГДЕ не выводится — ни в админке, ни в боте. Бот пишет дефолтный `shift_type`, день/ночь не спрашивает.
3. `attachments`: `kind` enum += `video`; `+ subtask_id INT NULL` (FK); `order_id` остаётся заполненным (он NOT NULL — пруф цепляем и к заявке, и к под-задаче). Хранение: `file_url` — первичен (своё хранилище), опц. `file_id TEXT` как кэш.
4. **`order_subtasks`**: `id, order_id, section_id (null), sub_no, status['pending','done','failed'], reason_code, comment, completed_at, completed_by_driver_id`. `unique(order_id, section_id)`. Материализуется при сохранении позиций; без участков — одна строка (`section_id=null`), показ `№35`; с участками — `№35.1/35.2`.
5. **`bot_sessions`**: `chat_id BIGINT PK, driver_id, state, context JSONB, updated_at`. Чистка по `updated_at`.
6. Привязка — `channels` (готов: `unique(type,external_id)` из `006`).

### Согласование с уже существующим (это НЕ greenfield)
- `orders.js:280-301` уже содержит `driverConfirm`/`fail`, закрывающие заявку **целиком** (`done`/`failed`, enum из `006`/`024`). Модель под-задач **заменяет** этот флоу. → нужна миграция совместимости и **регресс-тесты** (`orders-stage2`, `orders-complete`, `orders-create`), а не аддитивное изменение.
- Заявка без участков → одна под-задача; happy path сходится со старым «done».

### Жизненный цикл под-задачи и перенос
```
⏳ pending → ✅ done(+proof)            (навсегда)
⏳ pending → ⚠️ failed(reason+photo)
коммит «Завершить заявку»:
   все done            → заявка done
   часть не-done       → заявка обратно в пул (unassigned), живы только не-done; done скрыты
```
- Перенос = заявка снова в пуле распределения; менеджер раздаёт обычным drag-and-drop (дата/водитель = факт перетаскивания, без отдельной «даты переноса»). Остаток — одному водителю (раздача под-задач разным — будущее).
- Видимость: общий пул + фильтр-чип «Переносы» (причины, счётчик). Не отдельная система.

### Отображение задачи водителю (ДВА УРОВНЯ)
Задача водителю описывается на двух уровнях; эмодзи-контейнеры используются ТОЛЬКО на втором.
- **Шапка — кликабельный адрес → точка в Яндекс.Картах:** строка адреса = ссылка по координатам объекта (`https://yandex.ru/maps/?ll={lng},{lat}&z=17&pt={lng},{lat}`), иначе по тексту адреса. Водитель тапает — открывается точка, оттуда строит маршрут. Хелпер `yandexMapsUrl(o)` в `src/lib/orderUi.js`; в админке ссылка в `OrderModal` (готово). В боте — кликабельный URL в шапке сообщения заявки. Координаты отдаются в `listOrders` (`ob.lat/ob.lng`).
- **Уровень 1 — по участкам (текст, без эмодзи-контейнеров):**
  `📍 Участок 58 — Заменить 1`, `📍 Участок 63 — Заменить 1`. Действие (Поставить/Заменить/Забрать) + количество. Что полный увозим — подразумевается действием.
- **Уровень 2 — команда на базу (единственное место с эмодзи):**
  `📦 С базы взять: 📦×N (N пустых)`, где N = Σ(Поставить+Заменить) по всем участкам. Число эмодзи = число контейнеров (видно глазом).
- **Мелкой строкой:** `N рейсов` (по вместимости пустых машины; полный — 1 за рейс).
- Старая пара ⬜ пустой / 🟩 полный у каждой позиции УБРАНА («разные плоскости»). Эмодзи — только команда загрузки на базе.
- Реализация в админке — ГОТОВО: `src/components/admin/ContainerJob.jsx` переписан на два уровня (текст по участкам + команда `📦×N` + строка рейсов); функция `containerJobsBySection` удалена, используется `containerJob`. Бот переиспользует эту же модель при рендере сообщения.

### Медиа-пруф
- Нативная отправка (камера/голос Telegram) — загрузку делает клиент мессенджера (надёжно на слабой сети).
- На коммите бот получает `file_id` → **media worker** в фоне скачивает в своё хранилище (S3/MinIO/диск), пишет `attachments.file_url`. `file_id` — только кэш. Дохлая сеть водителя не блокирует коммит (скачивание отложенно). При смене токена/платформы (МАКС) архив не теряется.

### Кто что закрывает
- Работу закрывает **водитель** (под-задачи → happy path сам `done`). Менеджер работу не закрывает; его единственное действие по провалу — перетащить остаток (тот же drag-and-drop).
- Бухгалтерское `done → closed` — отдельно, не пересекается.

### Изоляция (на сервере)
- `services/driverScope`: бот всегда резолвит `chat_id → driver_id` и форсит фильтр; нельзя доверять `assigned_driver_id` как клиентскому параметру. Тест: чужой order → 403/пусто.

## Контракт событий (для клиентского бота — приёмник позже)
- **Переиспользовать существующий словарь outbox**, не плодить новый. Уже пишутся `order_assigned` (`orders.js:146`), `order_done`, `order_unassigned`, `order_failed`. Согласовать имена ДО эмиссии новых; «итог по участкам на коммите» — расширение существующего события, а не новый параллельный `order_scheduled`.
- Получатели (позже) — доверенные лица объекта/участка с привязанным каналом; изоляция по `client_id`. Тексты — в клиентском спеке.

## Testing Strategy
- vitest (сервис): `verifyCode`/привязка/идемпотентность; PIN + lockout; материализация под-задач и стабильность `sub_no`; коммит (happy/partial); возврат остатка в пул; **изоляция** (чужой order → 403/пусто); пробег старт/конец поверх present-by-default; **регресс** старых `driverConfirm/fail`.
- FSM бота: хендлеры с замоканным контекстом; состояние читается/пишется в `bot_sessions`.
- Прогон: `cd server && npx vitest run` (не с фильтром/списком файлов).

## Rollout Plan
1. Данные+админка: миграции (1–6), PIN + «личная ссылка» в `Drivers.jsx`, материализация `order_subtasks`.
2. Бот: привязка по ссылке, выход на смену (пробег), «Задачи на завтра», «Завершить смену».
3. Бот: список задач, отметка под-задач, пруф (+media worker), «Завершить заявку», перенос + фильтр «Переносы». Согласовать/мигрировать старый `driverConfirm/fail`.
4. События клиента: согласовать словарь, эмиссия в outbox.
5. Клиентский бот (pull + тексты) — отдельный спек.

Деплой: отдельный процесс, **отдельный `DRIVER_BOT_TOKEN`** в `.env`, long-polling, single-instance.
