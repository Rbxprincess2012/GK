# Справедливое распределение заявок между водителями — Design Specification

Date: 2026-06-07

## Problem Statement
Заявки на смену распределяются вручную (drag&drop по районам). Оплата водителю —
фиксированная за заезд, поэтому когда у одного водителя близкие к базе точки, а у
другого далёкие — возникают конфликты. Нужно интеллектуально и справедливо
распределять нагрузку с учётом числа заездов и расстояния до базы.

## Решённые вопросы (зафиксировано с заказчиком)
1. **Геокодинг** — автоматический (Яндекс/2ГИС/DaData) за абстракцией; ключ из настроек.
2. **Координаты правятся вручную**; ручная точка (`geo_source='manual'`) приоритетнее и
   НЕ перезатирается автогеокодером.
3. **Точка отсчёта километража — база** (`settings.base`). Свалка (`landfill`) вне дизайна.
4. **Справедливость** = минимизировать разброс «балла тяжести»
   `score = trips + km_weight · km` (прямое расстояние, гаверсинус). Число заездов может
   чуть отличаться. `km_weight` настраивается (дефолт 0.1 ⇒ 10 км ≈ 1 заезд).
5. **Алгоритм C** — жадный старт по районам + полировка парными обменами.
6. **Форма** — кнопка «Распределить»: алгоритм предлагает раскладку поверх текущего
   экрана, диспетчер правит существующим drag&drop, затем «Применить».
7. **Токены в Настройках** (Яндекс-геокодер, Telegram, MAX) — редактируют директор и
   менеджер; доступ к Настройкам открыт менеджеру.
8. **Километраж сохраняется в БД** на заказе при назначении (`distance_km`, `trips`,
   `load_score`) — для сравнения фактической нагрузки за период.

## Requirements
### Функциональные
- Геокодирование адреса объекта в lat/lng (авто) + ручной ввод/правка координат.
- Хранение координат базы; геокодинг адреса базы при сохранении настроек.
- Подсчёт расстояния точка→база (гаверсинус) и числа заездов по слотам/вместимости.
- Кнопка «Распределить»: подсказка-раскладка с метриками по каждому водителю.
- Применение раскладки одним действием; ручная корректировка через DnD остаётся.
- Запись `distance_km`/`trips`/`load_score` в заказ при назначении.
- Отчёт за период: суммарная фактическая нагрузка (заезды, км) по водителям.
- Поля токенов (Яндекс-геокодер, Telegram, MAX) в Настройках, доступ менеджеру.

### Нефункциональные
- Геокодер не настроен → распределение деградирует до баланса по числу заездов
  (с предупреждением), система не падает.
- Алгоритм считается на лету за < 1 c для нашего масштаба (десятки заявок).
- Секреты (токены) — в БД (`settings`), не в git.

## Architecture
### Данные (миграция)
- `objects`: + `geocoded_at timestamp`, + `geo_source text` (`yandex|manual|…`).
  (`lat`/`lng` уже есть.) Автогеокодер пропускает `geo_source='manual'`.
- `orders`: + `distance_km decimal(8,2)`, + `trips int`, + `load_score decimal(8,3)`.
  Заполняются при назначении/перерасчёте.
- `settings`: ключ `base` = `{address,lat,lng}` (есть), `integration_tokens` (есть,
  расширяем полями `yandex_geocoder_key`, `max_bot_token`), новый `distribution` =
  `{ km_weight: 0.1 }`.

### Бэкенд
- `lib/geocode.js` — `geocode(address) → {lat,lng,source,precision}|null`. Провайдер по
  настройке/env, ленивый импорт (как nodemailer у почты).
- `services/geocoding.js` — сборка адресной строки из объекта, `geocodeObject(id)`
  (не трогает manual), `backfillObjects()`.
- `services/settings.js` — добавить `getSetting(key)`/`setSetting(key,value)` (есть
  getTokens/setTokens).
- `lib/distribute.js` — чистые функции: `haversineKm`, `orderTrips(order,capacity)`,
  `score`, `suggest(orders, drivers, base, params)` (жадный + полировка). Без БД —
  тестируется юнит-тестами.
- `services/distribution.js` — собирает входные данные (заявки+координаты, водители на
  смене, база, params) и зовёт `lib/distribute.js`. `applyAssignments()` в транзакции
  пишет назначения + `distance_km/trips/load_score`.
- Маршруты: `POST /distribution/suggest`, `POST /distribution/apply`. Назначение через
  существующий путь дополняется записью метрик.
- `routes/settings.js` — `yandex_geocoder_key`, `max_bot_token` в схему; `base` и
  `distribution` через get/set; доступ к `/settings` расширить ролью `manager`.

### Фронтенд
- `Distribution.jsx`: кнопка «Распределить» → предпросмотр (подсветка предложенного
  водителя у заявки, бейджи по водителю: заезды/км/score, общий разброс). «Применить»
  (bulk) / «Сбросить». Предупреждение, если база не задана.
- Карточка объекта (`OrderModal`/clients object form): поля lat/lng + кнопка
  «Геокодировать»; пометка источника координат.
- `Settings.jsx`: секция токенов + Яндекс-геокодер + MAX; база переезжает в БД;
  поле `km_weight`. Доступно менеджеру.
- Отчёт (Reports): нагрузка по водителям за период (заезды, км).

## Implementation Details
### Заезды (trips)
`slots(item) = {place:1, replace:2, haul:1}[action] · quantity`;
`order_slots = Σ slots`; `trips = ceil(order_slots / capacity_slots)` (capacity по
машине водителя, дефолт 3).

### Балл тяжести
`km` — гаверсинус центра объекта до базы. `score = trips + km_weight·km`.
Балансируем суммарный `score` по водителям.

### Алгоритм (C)
1. Сгруппировать заявки по районам; внутри — по убыванию км.
2. Жадно: каждый следующий район/заявку отдать водителю с наименьшим текущим score,
   стараясь не дробить район.
3. Полировка: пока есть улучшающий парный обмен/перенос, уменьшающий
   `max(score)-min(score)` без роста геогр. разброса — применять. Ограничить число
   итераций.
4. Вернуть раскладку + метрики; заявки без координат — в группу «без гео» (баланс по
   заездам).

## Testing Strategy
- Vitest (есть): юнит-тесты `lib/distribute.js` (haversine, trips, баланс на фикстурах,
  детерминизм) и `lib/geocode.js` с мок-провайдером.
- Ручная проверка: backfill 31 объекта, «Распределить» → «Применить», метрики в заказе.

## Rollout Plan
1. Миграция (objects/orders/settings) + дефолт `distribution`.
2. Настройки: токены (геокодер+MAX), база в БД, `km_weight`; доступ менеджеру.
3. Геокодер + ручные координаты + backfill существующих объектов.
4. Алгоритм + suggest/apply + запись метрик при назначении.
5. UI распределения (кнопка/предпросмотр/применить).
6. Отчёт нагрузки за период.
Все изменения аддитивны: ручной DnD продолжает работать без алгоритма.
