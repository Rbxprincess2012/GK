# Этап 2 — Боты, голос/текст, ИИ-нормализация (дизайн)

Date: 2026-05-31
Зависит от: [Этап 1 — ядро](2026-05-31-dispatcher-core-design.md) (бэкенд Express+PostgreSQL уже готов).

## Problem Statement

Сейчас (Этап 1) диспетчер вносит заявки руками. Этап 2 автоматизирует **приём от
клиентов и выдачу водителям** через Telegram-ботов с распознаванием голоса и
ИИ-нормализацией свободного текста в структуру нашей БД. Человек (диспетчер) остаётся
точкой контроля: подтверждает заявку и распределяет.

## Scope (v1 Этапа 2)

- **В фокусе:** два Telegram-бота — **клиентский** и **водительский** (разные токены).
  Текст + голос. ИИ-нормализация. Согласование диспетчером. Уведомления клиенту и
  водителю. Подтверждение выполнения водителем с фото/текст/голос.
- **Позже:** MAX-мессенджер, телефонные звонки (запись→STT). Закладываем абстракцию
  каналов, но не реализуем в v1.

## Роли n8n и бэкенда

- **n8n** — весь обмен с мессенджерами: триггеры на входящие, STT, вызов LLM,
  отправка сообщений, инлайн-кнопки. Не хранит бизнес-данные.
- **Бэкенд (Express, Этап 1)** — единственный владелец данных. n8n создаёт/читает
  заявки **через REST API**. Бэкенд на смену статусов шлёт **события в n8n**
  (исходящие уведомления).
- Так бизнес-логика и БД — в одном месте (бэкенд), а интеграции — в n8n.

## Идентификация и каналы

- Таблица `channels` (уже есть): `owner_kind (client|driver)`, `owner_id`,
  `type (telegram|max|phone)`, `external_id (chat_id)`.
- **Онбординг:** первое сообщение с незнакомого chat_id → бот просит код/телефон для
  привязки к существующему заказчику/водителю (диспетчер заводит их в Этапе 1). Привязка
  пишет строку в `channels`. Незнакомцам без привязки заявки не оформляем.

## Поток КЛИЕНТА (приём заявки)

```
Клиент пишет боту (текст ИЛИ голос — как удобно)
  → n8n Telegram Trigger (клиентский бот)
  → определить chat_id → найти клиента (channels). Нет → онбординг.
  → тип сообщения:
       voice → скачать ogg → STT (распознавание) → текст
       text  → как есть
  → LLM-нормализация: свободный текст → СТРУКТУРА (JSON по схеме полей БД)
  → резолв объекта: сопоставить с объектами этого клиента (по неоф. названию/адресу)
       однозначно → object_id;  неоднозначно/новый → пометка need_review
  → бот возвращает клиенту СТРУКТУРИРОВАННЫЙ черновик + кнопки:
       [✏️ Редактировать]  [✅ Отправить диспетчеру]
  → Редактировать → Telegram Mini App (веб-форма, предзаполнена) → правка полей
  → Отправить → POST /orders (status = pending_review) + сохранить исходное
       сообщение и транскрипт в inbound_messages (привязка к заявке)
```

Доп. информация (время приезда, особые указания), не попавшая в структурные поля,
складывается в **текстовый комментарий заявки** (`orders.note`).

## Поток ДИСПЕТЧЕРА (согласование) — гибрид с фронтом Этапа 1

```
Заявки status=pending_review видны на фронте (Заявки/Распределение)
  → диспетчер проверяет структуру
  → [Заявка принята] → PATCH статус pending_review → new (accepted)
       → бэкенд шлёт событие order_accepted в n8n
       → бот клиенту: «Заявка принята в работу, №<number>»
  → диспетчер распределяет на водителя (assign, Этап 1)
       → бэкенд шлёт событие order_assigned в n8n
       → бот КЛИЕНТУ: №заказа, адрес объекта, ФИО водителя, телефон,
         госномер+марка машины, комментарий
       → бот ВОДИТЕЛЮ (водительский бот): задание отдельным сообщением
```

«ID присваивается при принятии» реализуем так: `orders.number` существует с создания,
но **клиенту он сообщается только на шаге order_accepted** (раньше клиент видит черновик
без номера).

## Поток ВОДИТЕЛЯ (выполнение)

```
Водительский бот: на каждое задание — отдельное сообщение с инлайн-кнопками
  [✅ Подтвердить выполнение]  [⛔ Не выполнено]

✅ Подтвердить → бот просит приложить подтверждение (фото/текст/голос; опционально)
   → голос → STT → транскрипт
   → POST /orders/:id/complete  (+ attachments[], при необходимости движения контейнеров)
   → статус done
   → авто-форвард подтверждения КЛИЕНТУ в его чат (фото/текст) → диспетчер жмёт
     [Отправлено] или авто → close (по правилу Этапа 1 «отправлено = закрыта»)

⛔ Не выполнено → бот просит причину (текст/голос) → сохраняем в note/attachment,
   статус → cancelled (или новый failed) + уведомление диспетчеру
```

Замечание: фактические **номера контейнеров** (движения) водитель в чат-боте вводит
неудобно. Варианты: (а) в v1 водитель только подтверждает + прикладывает пруф, а
движения/инвентарь проставляет диспетчер на фронте; (б) позже — мини-апп водителя со
сканом/выбором номеров. Рекомендация v1 — вариант (а).

## ИИ-компоненты и модели (рекомендации)

**STT (голос → текст), русский:**
- **Рекомендую: OpenAI `gpt-4o-transcribe`** (или `whisper-1`) — отличный русский, прост
  в n8n (HTTP-нода/OpenAI-нода).
- **Альтернатива под RU/телефонию: Yandex SpeechKit** — нативный русский, пригодится для
  звонков на Этапе MAX/phone.
- Про **Grok**: голосовой STT у него менее обкатан для русского — лучше Whisper/4o.

**Нормализация (текст → структура), строгий JSON:**
- **Рекомендую: LLM со Structured Outputs / JSON-schema** — OpenAI `gpt-4o`/`gpt-4.1`
  (Structured Outputs) **или** Anthropic Claude (tool use) для гарантированной структуры.
- Для экономии можно `gpt-4o-mini`/Claude Haiku на извлечение, но качество маппинга
  адреса/действий лучше у старших моделей — рекомендую старшую на нормализацию.

**Схема нормализации (выход LLM)** — повторяет поля создания заявки:
```json
{
  "items": [
    { "action": "place|replace|haul", "container_type": "стандартный",
      "quantity": 1, "waste_class": "4|5|null" }
  ],
  "object_hint": "ЖК Маршалл / ул. ... ",   // текст для резолва объекта
  "payment_method": "cashless|cash|null",
  "desired_date": "YYYY-MM-DD|null",
  "desired_time": "HH:MM|null",
  "comment": "доп. информация свободным текстом",
  "ambiguities": ["что непонятно — для пометки диспетчеру"]
}
```
Промпт даёт модели контекст: список объектов клиента (имена/адреса), словарь действий
(«поставить/заменить/забрать/вывезти»), тип контейнера «лодочка», классы 4/5.

## Интеграция бэкенд ↔ n8n

**Входящее (бот → система):** n8n вызывает наш REST (`POST /orders`,
`POST /orders/:id/complete`, …). Защита: сервисный токен (заголовок `Authorization`),
проверяемый middleware бэкенда.

**Исходящее (система → бот):** бэкенд на смену статуса POST'ит событие на webhook n8n:
- `order_accepted` → текст клиенту с номером;
- `order_assigned` → клиенту (детали) + водителю (задание);
- `order_done` → форвард пруфа клиенту.
n8n берёт chat_id из `channels` (через API бэкенда) и шлёт сообщения нужным ботом.

Альтернатива webhook'ам — таблица `outbox` (события), которую n8n опрашивает; webhook
проще для v1.

## Изменения в данных (Этап 2)

- **orders.status**: добавить `pending_review` (черновик от клиента, ждёт диспетчера) и,
  опц., `rejected`/`failed`. Миграция меняет CHECK-ограничение enum.
- **inbound_messages** (уже есть): хранит исходный текст/голос-URL/транскрипт + связь с
  заявкой (`linked_order_id`).
- **outbound_log** (опц.): что и кому отправили (для идемпотентности/повторов).
- **clients**: код/верификация для онбординга канала (или сверять по телефону).

## Список n8n-воркфлоу

1. **client-intake** — Telegram Trigger (клиентский бот) → тип → STT → LLM → резолв →
   черновик с кнопками → создание заявки pending_review.
2. **client-edit (Mini App)** — отдаёт предзаполненную форму, сабмит → PATCH/создание.
3. **outbound-notify** — webhook от бэкенда (accepted/assigned/done) → сообщения клиенту/
   водителю.
4. **driver-tasks** — отправка заданий водителю (вызывается из outbound-notify на assign).
5. **driver-complete** — Telegram callback (кнопки) водительского бота → сбор пруфа →
   STT → `complete`/`cancel`.
6. **onboarding** — привязка незнакомого chat_id к клиенту/водителю.

## Edge cases / failure modes (требуют решения)

- Несколько объектов с похожими именами → дизамбигуация (бот уточняет / диспетчер).
- Голос плохого качества / шум → низкая уверенность STT → показать транскрипт клиенту на
  подтверждение.
- Клиент шлёт несколько заявок одним сообщением → LLM возвращает несколько `items`/заявок.
- Идемпотентность: повтор webhook'а не должен слать дубль сообщений (ключ события).
- Клиент редактирует после отправки диспетчеру → блокировать после accepted или версия.
- Водитель жмёт «Не выполнено» → маршрут/инвентарь не меняются; нужна причина.
- Привязка канала: защита от чужого chat_id (верификация кодом/телефоном).
- Стоимость/лимиты LLM/STT; ретраи; логи в inbound/outbound.

## Ревизия v2 (по итогам независимого ревью)

Ревью показало, что v1-схема опиралась на несуществующие в бэкенде статусы/эндпоинты и
имела две логические нестыковки. Ниже — обязательные предусловия и принятые решения.

### Предусловия по бэкенду (строим ДО воркфлоу n8n)

**Миграция 006:**
- `orders.status`: добавить `pending_review` и `failed` (пересоздать CHECK-enum).
- `orders`: добавить `accepted_at`, `fail_reason`.
- `channels`: уникальность `(type, external_id)`, индекс `(owner_kind, owner_id)`,
  поля онбординга `verify_code`, `verify_expires_at`, `verified_at`.
- `inbound_messages`: `external_message_id` + уникальность (дедуп Telegram-апдейтов).

**Миграция 007 — `outbox`:** `id, event_type, order_id, payload jsonb,
event_key (uniq), status (pending|sent), created_at, delivered_at`. Исходящие
уведомления идут через outbox + поллер/подтверждаемый webhook n8n (не fire-and-forget).

**Новые эндпоинты:**
- `POST /orders` — принимать `status='pending_review'` (или `POST /orders/draft`).
- `POST /orders/:id/accept` (`pending_review → new`, `accepted_at`, событие
  `order_accepted`, **присвоение `number` здесь**, см. ниже).
- `POST /orders/:id/fail` (`assigned|in_progress → failed`, причина, событие диспетчеру).
- `POST /orders/:id/driver-confirm` — статус → `done` + attachments (БЕЗ движений).
- `POST /orders/:id/movements` — диспетчерская фиксация движений контейнеров и инвентаря,
  **развязана** со сменой статуса (см. «инвентарь»).
- `channels` CRUD + `POST /channels/resolve` + онбординг-верификация.
- `inbound_messages` POST (сырьё + транскрипт + `linked_order_id`).
- «Богатый» `GET /orders/:id` с джойнами driver/vehicle/object (для уведомлений).
- **Auth middleware** (сервисный токен) на маршруты, дёргаемые n8n.
- **Статус-гарды** во всех переходах: `where({ id, status: <ожидаемый> })` (анти-гонки).

### Принятые решения по нестыковкам

1. **Нумерация:** черновики `pending_review` **не получают `number`**. `number`
   присваивается в момент `accept`. Нет дыр в сквозной нумерации для счетов.
   *(Требует: убрать `number serial`-дефолт у черновиков → присваивать из последовательности
   при accept.)*
2. **Инвентарь vs водитель (РЕШЕНО для v1):** в боте **номера контейнеров не ведём**.
   - **Водитель** «Подтвердить выполнение» → `driver-confirm`: статус `done` + пруф
     (фото/текст/голос). Движения контейнеров НЕ пишутся.
   - Точный учёт инвентаря по номерам (`/orders/:id/movements`, опц. на фронте у
     диспетчера) — **отложен** до отдельного решения (мини-апп водителя или ручной ввод
     диспетчером позже). Бэкенд это умеет (Этап 1), просто в боте v1 не используем.
   - `close` — как в Этапе 1 («отправлено клиенту = закрыта»).
3. **«Не выполнено» → `failed`** (не `cancelled`): причина сохраняется, заявку можно
   переназначить (вернуть в `new`/переassign).
4. **`in_progress`:** «Подтвердить выполнение» можно трактовать как `assigned → done`
   напрямую (v1). `in_progress` оставляем для ручной отметки «водитель в пути» (опц.).
5. **Онбординг:** одноразовый код от диспетчера со сроком (`verify_code`), а не сверка по
   телефону. Привязка идемпотентна (uniq на chat_id).
6. **Идемпотентность:** outbox + `event_key`; входящие — дедуп по `external_message_id`.
7. **LLM-схема расширяется:** массив заявок по разным объектам (несколько `orders`);
   поле под конкретные номера контейнеров (→ `order_item_containers`); ветка
   `requires_photo` (если у клиента/объекта true — пруф-фото обязателен для `driver-confirm`).
8. **Дизамбигуация объекта:** если объект не разрешён в `object_id` — заявку НЕ создаём
   (модель требует `object_id`); черновик висит на стороне бота/Mini App как «need_review»,
   диспетчер уточняет, и только потом `POST /orders`. (Либо позже — таблица `order_drafts`
   без жёсткого FK на объект.)

### Порядок реализации (снизу вверх)

Бэкенд (миграции 006–007 + эндпоинты + auth) → затем воркфлоу n8n в порядке:
**onboarding → outbound-notify(outbox) → client-intake → driver-tasks →
driver-complete → client-edit(Mini App)**.
